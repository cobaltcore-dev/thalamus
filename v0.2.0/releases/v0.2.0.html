What's new in v0.2.0 ​

v0.2.0 is a breaking release. It consolidates the two v0.1.0 charts (thalamus-crds + thalamus) into a single self-contained thalamus chart, stops the chart from managing your Gateway, and refactors the Model CRD around corev1.PodSpecs.

  • One chart instead of two. v0.1.0 shipped thalamus-crds (the Thalamus, Gateway API, inference extension, and agentgateway CRDs) alongside thalamus (operator + data plane). The v0.2.0 chart bundles all CRDs, so CRD schema and operator version stay in sync and installs need only one release.
  • Gateway ownership changes. In v0.1.0 the chart rendered the Gateway, AgentgatewayParameters, and AgentgatewayPolicies. Since v0.2.0 you create and manage the Gateway and its related configuration yourself. The routing policies are now owned and reconciled by the operator instead, so unintended, breaking manual changes are automatically reverted.
  • PodSpec-based serving. spec.serving.engine and spec.serving.router are now corev1.PodSpecs with named containers engine and router. Any Kubernetes pod field (tolerations, volumes, probes, sidecars, …) becomes usable without bespoke CRD fields.
  • Old EPP is now the router. spec.serving.epp becomes spec.serving.router.
  • Model aliases. spec.aliases exposes the model at the Gateway under up to five extra names, and enables dynamic renaming without restarting the engine.
  • Scheduling moved into the pod spec. Old spec.scheduling.nodeSelector moves to spec.serving.engine.nodeSelector etc. (tolerations, volumes, and other pod-level fields are now supported).
  • weights.hf.tokenSecret is now optional when weights need no authentication.
  • open-webui is no longer bundled as a chart dependency. Install it as a separate release if you use it.

Migrating from v0.1.0 ​

Follow the steps below to upgrade your Thalamus deployment from v0.1.0 to v0.2.0 while ensuring model availability. Alternatively, you can tear down Thalamus altogether for a simpler upgrade using helm uninstall thalamus, but this will terminate your currently running models.

1. Backup your models ​

bash
kubectl get models --all-namespaces -o yaml > models-backup.yaml

2. Consolidate to the single chart and upgrade the stack ​

Upgrade the thalamus release with --take-ownership so the new chart can adopt the CRDs that the thalamus-crds release previously owned. Scale the operator to zero in the same step. This applies the new CRD schema and the new operator image in one shot, without the operator touching any old-schema objects. If you need zero downtime, keep your Gateway across the upgrade:

bash
kubectl -n thalamus annotate \
  gateways.gateway.networking.k8s.io/inference-gateway \
  helm.sh/resource-policy=keep --overwrite
helm upgrade --install thalamus oci://ghcr.io/cobaltcore-dev/charts/thalamus \
  --namespace thalamus --create-namespace --wait \
  --version v0.2.0 \
  --set operator.replicas=0 \
  --take-ownership

The upgrade re-parents every CRD to the thalamus release. Do not run helm uninstall thalamus-crds. Uninstall deletes the resources listed in that release's manifest, including the CRDs you just adopted. The old release no longer owns anything, so just forget its Helm record (run this only after the upgrade above, which re-parents the CRDs):

bash
kubectl delete secret --namespace thalamus -l owner=helm,name=thalamus-crds

If your cluster already provides any of the bundled CRDs, disable them, e.g. --set gateway-api.enabled=false.

3. Recreate the Gateway ​

v0.1.0 created the Gateway and AgentgatewayParameters from the chart, so on upgrade Helm deletes them. v0.2.0 does not manage the Gateway, but users are expected to create their own, e.g. by applying the example manifest:

bash
kubectl apply -f https://raw.githubusercontent.com/cobaltcore-dev/thalamus/v0.2.0/examples/gateway.yaml
kubectl wait gateway/inference-gateway \
  --namespace thalamus --for=condition=Programmed=True --timeout=120s

4. Rewrite your Model resources in the new schema ​

Every setting under spec.serving is restructured into the PodSpec shape. You need to manually adjust the configuration and create a models-v0.2.0.yaml file, then apply it to the cluster:

bash
# edit the manifests into the new shape, then:
kubectl apply -f models-v0.2.0.yaml

For example, translating a model to the v0.2.0 shape looks like this:

diff
@@ spec:
   backend: native
   replicas: 1
-  scheduling:
-    nodeSelector:
-      disktype: ssd
   serving:
     engine:
-      image: docker.io/vllm/vllm-openai:v0.26.0
+      containers:
+        - name: engine
+          image: docker.io/vllm/vllm-openai:v0.32.0
           args:
             - --disable-uvicorn-access-log
             - --gpu-memory-utilization=0.95
             - --tensor-parallel-size=2
             - --default-chat-template-kwargs={"enable_thinking":true}
             - --reasoning-parser=qwen3
             - --speculative-config={"method":"mtp","num_speculative_tokens":2}
             - --enable-auto-tool-choice
             - --tool-call-parser=qwen3_coder
           env:
             - name: NCCL_IB_DISABLE
               value: "1"
           resources:
             requests:
               nvidia.com/gpu: 2
             limits:
               nvidia.com/gpu: 2
+      nodeSelector:
+        disktype: ssd
-    epp:
+    router:
+      containers:
+        - name: router
           image: ghcr.io/llm-d/llm-d-router-endpoint-picker:v0.9.0
           resources:
             requests:
               cpu: 100m
               memory: 256Mi
             limits:
               cpu: 200m
               memory: 512Mi
   weights:
     type: hf
     hf:
       repoId: Qwen/Qwen3.6-27B
       tokenSecret:
         name: hf-token
         key: HF_TOKEN

Notes:

  • Each containers entry needs name and image; additional containers of other names are added as sidecars.
  • tokenSecret is now optional; keep it if you still want to authenticate to Hugging Face.
  • Because the same model name/namespace/kind is kept, the operator reconciles into the same object. Its engine/router workloads are recreated under the new shape when it comes back up.

5. Scale the operator back up ​

bash
helm upgrade --install thalamus oci://ghcr.io/cobaltcore-dev/charts/thalamus \
  --namespace thalamus --create-namespace --wait \
  --version v0.2.0 \
  --set operator.replicas=1

The operator should now pick up the new model specs and perform an in-place rolling update of the engine and router deployments.

6. Verify ​

bash
kubectl get models --namespace thalamus
kubectl wait model/<model-name> --namespace thalamus --for=condition=Ready --timeout=600s
kubectl logs deploy/thalamus-operator --namespace thalamus  # no reconciliation errors
